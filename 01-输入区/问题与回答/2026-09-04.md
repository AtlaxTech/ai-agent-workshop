## 记录 2：PyCharm 能跑、Trae 报 SOCKS 代理错误，换 IDE 要重装依赖吗

- **日期时间**：2026-09-04 16:56
- **关联主题**：AI应用/实战/AI智能伴侣、Python 环境（venv）、环境变量、httpx 代理
- **状态**：已回答（用户未确认修复结果）

### 问题原文

> `Terminal`为啥我在pycharm运行的好好的，换到trae就报错？难不成每切换一个IDE就要把所有依赖和包都重新安装一遍么？
>
> （附 Trae 控制台报错：streamlit run ai_assitant.py 时，第 45 行 `ollama_client = OpenAI(...)` 处抛出 `ImportError: Using SOCKS proxy, but the 'socksio' package is not installed. Make sure to install httpx using pip install httpx[socks].`，traceback 显示解释器路径为 `/Library/Frameworks/Python.framework/Versions/3.13/...`）

### 回答正文

先直接回答：**不需要换 IDE 就重装依赖**。依赖不是装在 IDE 里的，是装在"Python 环境"里的。IDE 只是个启动器：它帮你挑一个 Python 解释器来跑脚本，顺便把启动它自己的那个终端里的一堆设置（环境变量）一起带上。你这次撞上的，是"两个 IDE 指向的 Python 环境不同 + 启动时带的环境变量不同"两件事叠加。

#### 这个报错到底在说什么

一整屏 traceback 只需要看最后一行：`ImportError: Using SOCKS proxy, but the 'socksio' package is not installed`。

翻译成大白话：OpenAI 库底层用 httpx 发 HTTP 请求。httpx 默认会"信任环境"（trust_env）——读一读系统里有没有设置代理。它发现你机器上有个 SOCKS 代理（通常是 `ALL_PROXY=socks5://...` 这样的环境变量，一般来自终端里配置的代理软件），于是想走这个代理；但走 SOCKS 代理需要一个小包 `socksio`，当前环境里没装，于是直接崩了。

注意崩的位置：traceback 指着 [第 45 行](file:///Users/qilong.lu/WorkDir/外置赛博大脑/30-学习与成长/ai-agent-workshop/01-输入区/AI应用/实战/practice-app/AI智能伴侣/ai_assitant.py#L45) `ollama_client = OpenAI(...)`。也就是说，**还没开始聊天，光"创建客户端对象"这一步就崩了**——因为 httpx 在创建客户端时就要根据代理设置搭好传输通道，而不是等到真正发请求时才发现。

#### 为什么 PyCharm 里好好的

两个可能的原因，都和"IDE 本身"无关：

1. **Python 解释器不同**。traceback 里的路径是 `/Library/Frameworks/Python.framework/Versions/3.13/...`，说明 Trae 这次用的是系统全局的 Python 3.13。PyCharm 项目通常绑定的是项目自己的 venv（虚拟环境），两个环境里装的东西可以完全不同。
2. **环境变量不同**。SOCKS 代理来自环境变量。如果你是从一个配置了代理的终端启动 Trae（或 Trae 继承了 shell 配置），它就会带上这些变量；PyCharm 从图形界面（Dock/Spotlight）启动时不经过终端，自然没有这些变量。同一个解释器，也可能因此一个崩一个不崩。

其实你早就遇到过这个问题：你在 `ask_grok` 里给 httpx 写 `trust_env=False`（[第 163 行](file:///Users/qilong.lu/WorkDir/外置赛博大脑/30-学习与成长/ai-agent-workshop/01-输入区/AI应用/实战/practice-app/AI智能伴侣/ai_assitant.py#L163)），就是为了"别读系统代理设置"。这次是 OpenAI 库内部的 httpx 在读。

#### 怎么验证（最小例子）

在 PyCharm 和 Trae 的终端里分别跑这两条，对比输出：

```bash
python3 -c "import sys; print(sys.executable)"   # 看两边用的是不是同一个解释器
env | grep -i proxy                              # 看哪边带着代理环境变量
```

如果 Trae 那边多出 `ALL_PROXY=socks5://...` 之类的输出，谜底就揭晓了。

#### 解决方向（自己选，不替你改）

- 方向 A：给 Trae 用的那个 Python 补上 SOCKS 支持：`python3 -m pip install "httpx[socks]"`（注意"哪个解释器用就得装到哪个解释器里"）。
- 方向 B：代码层面让 OpenAI 客户端无视系统代理：`OpenAI(..., http_client=httpx.Client(trust_env=False))`——和你 grok 代码的思路一致。本地 Ollama 和国内 GLM 都不需要代理。
- 方向 C（长期正确姿势）：给项目建一个 venv，然后在 PyCharm 和 Trae 里都把解释器指向同一个 `.venv/bin/python`。之后换任何 IDE 都是零成本，因为大家用的是同一个环境。

#### 常见误区

- "依赖是装在 IDE 里的" → 不是。IDE 只是帮你调用某个解释器；包全部装在解释器对应的 site-packages 目录里。
- "报错一大屏就很难" → 只看最后一行（这里是 ImportError），往上的十几层全是"调用路径"，告诉你它是怎么走到这一步的。
- "换 IDE 要重装包" → 换"环境"才要装。让两个 IDE 用同一个 venv，就永远不存在这个问题。

#### 理解检查（自己想一想，不用回我）

## 记录 3：PyCharm 终端装过的包，为什么 Trae 里还要再装一遍

- **日期时间**：2026-09-04 17:15
- **关联主题**：Python 环境（venv）、pip 与解释器的绑定关系、IDE 终端与环境变量
- **状态**：已回答（用户未确认验证结果）

### 问题原文

> 我当然知道是因为'socksio' package 没有安装。我问的就是这个问题。为什么我在pycharm那边通过终端已经安装过了，到trae还要再安装一遍？IDE中的终端用的不都是本机环境的终端么？难不成两个IDE还用了两套不一样的终端环境？

### 回答正文

对，你猜的方向是对的：**两个 IDE 的"环境"确实可以不是同一套**。但要说准确点：终端程序本身是同一个（都是你本机的 zsh），不一样的是终端里激活的 **Python 环境**。而 `pip install` 装到哪，不看"哪台电脑、哪个终端"，只看一件事——**当前排在 PATH 第一位的是哪个 Python**。

#### 核心机制：pip 是跟着 Python 走的

一台电脑上可以同时存在很多个 Python：macOS 自带的、python.org 官方安装的（就是 traceback 里那个 `/Library/Frameworks/Python.framework/Versions/3.13`）、Homebrew 装的、Anaconda 的，以及每个项目自己的 venv。有几个 Python，就有几个 pip，各自有**各自独立的 site-packages 仓库**。

`pip install xxx` 永远只装进"它自己绑定的那个 Python"的仓库，不会装给其他 Python。

#### 你的情况大概率是这样

1. PyCharm 有个默认行为：打开项目终端时**自动激活**项目绑定的 venv（默认设置里叫 "Activate virtualenv"）。所以你在 PyCharm 终端里敲 `pip install socksio`，装进的是那个 venv 的仓库。
2. Trae 的终端没有激活任何 venv，PATH 里第一位的 Python 是系统全局的 Python 3.13。Trae 里跑 `streamlit run` 用的就是这个全局 Python——traceback 的解释器路径就是证据。
3. 于是：socksio 在 venv 的仓库里躺着（没丢，PyCharm 里照样能用），但全局 Python 的仓库里没有。Trae 用全局 Python，自然找不到。

所以严格说不算"再装一遍"——是两次安装落进了**两个不同的仓库**。

#### 怎么验证（最小例子）

在两个 IDE 的终端里各跑一遍：

```bash
which python3        # PATH 里排第一的 python3 是谁
pip -V               # pip 会自报家门：属于哪个 Python、哪个 site-packages
pip show socksio     # 这个环境里装没装、装在哪
```

`pip -V` 的输出类似 `pip 24.0 from /某路径/site-packages/pip (python 3.13)`，直接看路径就能确定"装到了哪"。两边一对比，结论一目了然。

#### 以后怎么避免（讲解，不替你改）

- 习惯一：用 `python3 -m pip install xxx` 代替裸 `pip install xxx`。这样"装给谁"就锁定为你敲的那条命令里的 python3，不会取决于 PATH 巧合。
- 习惯二（一步到位）：给项目建一个 venv（`python3 -m venv .venv`），PyCharm 和 Trae 的解释器设置都指向 `.venv/bin/python`；在终端里装包前先 `source .venv/bin/activate`。两个 IDE 共用一个环境之后，就不存在"换边要重装"。

#### 常见误区

- "终端是本机的，所以 pip 也是全局同一个" → 终端是本机的没错，但 pip 跟着"当前激活的 Python"走，不跟着终端走。
- "在 PyCharm 终端装过 = 装到电脑上了" → 只装进了当时激活的那个环境。换环境就要重新面对这个环境里有什么。
- "venv 是 PyCharm 的功能" → venv 是 Python 自带的标准库能力（`python3 -m venv`），PyCharm 只是帮你创建和激活得更勤快。

>

### 回答正文

不再纠结终端归属，直接在用户机器上实查证据定案：

**实查证据（Agent 在本机实际执行命令所得）：**

1. socksio 确实已安装，全机器唯一一份在仓库根目录的虚拟环境里：
   `ai-agent-workshop/.venv/lib/python3.13/site-packages/socksio`（同仓还有 streamlit 1.62.0、openai 3.6.0、httpx 0.28.1）。
2. Trae 预览实际运行的是另一个解释器（traceback 路径 `/Library/Frameworks/Python.framework/Versions/3.13`），其 site-packages 是另一套：streamlit 1.51.0、openai 2.7.1、httpx 都在，**没有 socksio**。

4. 本机环境确实带 Clash 代理变量 `ALL_PROXY=socks5h://127.0.0.1:7898`（另有 HTTP_PROXY 等同族变量），这是 httpx 要求 SOCKS 支持的触发器。

**结论因果链：** Trae 运行选了全局 Python（无 socksio）＋ 运行环境带 SOCKS 代理变量（httpx 必须走 SOCKS）→ 两条件同时命中 → ImportError。PyCharm 侧至少一个条件不成立（用的是 .venv，或启动时未继承代理变量），所以正常。与哪个终端、哪个 IDE 无关，取决于"这次运行选了哪个解释器"。

**修复路径（二选一）：**

- 路 A（推荐）：让 Trae 使用 `.venv`——解释器指向 `ai-agent-workshop/.venv/bin/python`，或终端 `source .venv/bin/activate` 后再 `streamlit run`。注意 `.venv` 在仓库根目录，app 在深层子目录，需确认 Trae 工作区覆盖到仓库根。`.venv` 里 streamlit/openai 版本更新（1.62.0 / 3.6.0）。

### 回答正文

**直觉**：流式输出的本质是服务器不一次给整段话，而是一小段一小段地发（chunk）。`stream=True` 让 SDK 不再"等完整答案、返回一个完整对象"，而是立刻给你一个"片段发生器"，你边收边显示。Streamlit 里的流式展示，就是"在同一个屏幕区域反复刷新文本"。

**你现在的代码在 stream=True 下必崩**：第 86 行 `response.choices[0].message.content` 是"非流式对象"的取法；stream=True 时返回的是 Stream 迭代器，没有 `.choices[0].message`，会直接 AttributeError。注释"非Stream方式解析方式"恰好说反了。

**关键三个点：**

1. `stream=True` → 返回可迭代对象，每段内容在 `chunk.choices[0].delta.content`（注意是 `delta` 不是 `message`），且部分 chunk 的 content 可能为 None（比如只带 role 的首块），要判空。
2. `st.write_stream(生成器)` → 消费生成器、在同一容器里打出打字机效果，结束后把**完整拼接的文本作为返回值**还给你。
3. 完整返回值 append 进 `st.session_state.messages`——记忆里永远存完整文本，屏幕上才有流式效果；不存完整版就会回到"历史被吞"的问题。

**改法示例（ask_glm 流式版）：**

```python
def ask_glm():
    stream = glm_client.chat.completions.create(
        model=glm_model,
        messages=st.session_state.messages,   # 顺手修掉"只发 system、没有记忆"的问题
        stream=True,
    )
    for chunk in stream:
        delta = chunk.choices[0].delta.content if chunk.choices else None
        if delta:
            yield delta
```

**要点解释：**

- **日期时间**：2026-09-04 17:59
- **关联主题**：AI应用/实战/AI智能伴侣、Python 生成器（yield / yield from）、惰性求值、多 provider fallback、st.write_stream

### 回答正文

用户担心的两个问题其实是同一个根源：**生成器是"懒"的**。

**1. 根源：带 yield 的函数，调用时一行都不执行**

`def` 里只要有 `yield`，调用 `ask_ollama()` 就不会执行任何代码，只会立刻返回一个"待办凭证"（生成器对象）；真正开始跑，是有人开始迭代它的那一刻（这里是 `st.write_stream` 消费它）。

由此推出两个连锁后果，方向和用户的直觉相反：

- `ask_ai` 里的 `try: return ask_ollama()` 的 try 块里**什么都不会发生**——Ollama 连不上也不会在此刻报错，`except OpenAIError` 永远接不到，fallback 形同虚设。错误会推迟到 UI 消费生成器时才炸，而且是没被兜住的炸。
- 输入框里 `ai_response = ask_ai("ollama")` 拿到的是"待办凭证"不是文本：`st.write()` 写它没有意义，`messages.append(生成器对象)` 更是把一个一次性的生成器存进了历史，下一轮重跑直接坏掉。

**2. 处理方案（三步）**

第一步：统一接口——三个 provider 都做成生成器。

```python
def ask_glm():
    stream = glm_client.chat.completions.create(
        model=glm_model,
        messages=st.session_state.messages,
        stream=True,
    )
    for chunk in stream:
        delta = chunk.choices[0].delta.content if chunk.choices else None
        if delta:
            yield delta


def ask_grok():
    # 原来的 httpx 请求不变，最后只 yield 一次完整字符串
    result = response.json()
    yield result["choices"][0]["message"]["content"]
```

grok 变成"只吐一大口的生成器"，没有打字机效果但接口统一，ask_ai 只需面对一种形状。

第二步：ask_ai 自己也改成生成器，fallback 靠"试探第一口"：

```python
def ask_ai(provider="auto"):
    if provider == "ollama":
        yield from ask_ollama()
    elif provider == "glm":
        yield from ask_glm()
    elif provider == "grok":
        yield from ask_grok()
    elif provider == "auto":
        for make_gen, name in ((ask_ollama, "Ollama"), (ask_glm, "GLM"), (ask_grok, "Grok")):
            gen = make_gen()          # 只领"待办凭证"，还没执行
            try:
                first = next(gen)     # 真正开始执行；连不上会在这里抛
            except StopIteration:
                print(f"{name} 返回空回复，尝试下一个...")
                continue
            except Exception as error:   # 兜底层故意放宽，覆盖 OpenAIError 和 httpx 错误
                print(f"{name} 调用失败：", error)
                continue
            print(f"使用 {name}...")
            yield first               # 先交出第一个片段
            yield from gen            # 再转发剩余全部片段
            return
        raise RuntimeError("所有 provider 都不可用")
    else:
        raise ValueError(f"不支持的 provider: {provider}")
```

原理：`next(gen)` 之前代码不执行；`next` 会推动生成器执行到第一个 yield。如果连接阶段就失败，异常发生在 `next()` 这一行内部，正好被 try 接住 → 换下一个 provider。本质是"把惰性执行往前推一格，用它来探测服务是否活着"。`yield from` 是"把另一个生成器的产出全部转发"的简写。

第三步：输入框消费流，把完整文本写回记忆：

```python

    st.chat_message("user").write(prompt)
    st.session_state.messages.append({"role": "user", "content": prompt})

    with st.chat_message("assistant"):
        full_reply = st.write_stream(ask_ai("ollama"))

    st.session_state.messages.append({"role": "assistant", "content": full_reply})
```

**3. 诚实的边界**

这个方案只覆盖"第一个片段都拿不到"的失败（连不上、认证失败、立刻报错）。如果流到一半断掉，前半截已经显示出去了，无法干净地重启 fallback（会出现重复的半截回答）——真实产品对这种情况有更复杂的处理（如 UI 标注部分失败、断点续传）。学习项目先接受这个边界。

**常见误区：**

- "调用生成器函数会执行函数体" → 不会，只返回生成器对象，直到被迭代。
- "try 包住 return ask_ollama() 就能兜底" → 兜不到，错误发生在消费阶段而非返回阶段。
- "把生成器对象直接 append 进 messages" → messages 里存的是一次性对象，重跑渲染和历史上下文都会坏。
- "except OpenAIError 就够了" → grok 走 httpx，抛的是 httpx 的错误；在多 provider 兜底这一层故意用 Exception 放宽并打日志，是合理的。

## 记录 8：with 是干什么的

- **日期时间**：2026-09-04 18:08
- **关联主题**：Python 基础（with 语句 / 上下文管理器）、Streamlit st.chat_message
- **状态**：已回答

### 问题原文

> with是干什么的？

（上下文：用户在记录 7 的方案里看到 `with st.chat_message("assistant"): placeholder = st.empty()`。）

### 回答正文

**直觉**：`with` 是"借场地，用完自动归还"。固定格式：

```python
with 某个东西 as 变量:
    # 缩进块里干活
# 一出这个块，"收尾工作"自动执行
```

进入缩进块之前，`with` 后面那个对象先做**准备工作**；缩进块结束（或中途报错）时，自动做**收尾工作**。你不用手动收尾，Python 保证一定执行。

**两个你身边就能看到的例子：**

```python
# 例 1：文件。出块自动 close，哪怕中间报错也 close，不会忘记关。
with open("a.txt") as f:
    text = f.read()

# 例 2：你代码里的 st.chat_message。块内创建的所有元素，都归属到这个 assistant 气泡里。
with st.chat_message("assistant"):
    placeholder = st.empty()   # 这个"坑"挖在 assistant 气泡里
```

对应到你流式输出的代码：`with st.chat_message("assistant"):` 的意思是"接下来我建的东西都放进 assistant 气泡"。出了这个块，气泡和 placeholder 都还在页面上，`placeholder.markdown(...)` 随时可以继续刷新——`with` 结束只是"收尾"（结束归属关系），不是"销毁对象"。

**准确定义（一句带过）**：`with` 是 Python 的上下文管理器语法，调用对象的 `__enter__`（进入时准备）和 `__exit__`（离开时收尾，包括异常时）两个方法。记不住这些名字没关系，先记住"借场地、用完自动归还"。

**常见误区：**

- "出了 with 块，块里创建的对象就被销毁了" → 不是。只是执行了收尾动作：文件被关闭（之后不能再读），气泡归属结束（但 placeholder 这个引用还能用）。
- "with 只是为了代码好看" → 核心价值是**保证收尾一定执行**，等价于 try/finally 的简化写法。

关键在第 238 行：`ask_ai("ollama", placeholder)` 把**这个坑的引用**当作参数传了进去。Python 传对象传的是引用——函数参数 `placeholder` 和外面的 `placeholder` 指向页面上**同一个坑**。所以"往里写东西"没有发生在输入框那里，而是发生在 `ask_ollama` 函数内部的第 65-66 行：每收到一段文本，就按一次"遥控器"刷新那个坑。写内容和创建坑是两个地点、同一个对象。

**逐行解释 L61-66**

前提：第 55-59 行 `stream=True` 时，`response` 不是完整答案，而是一个"片段流"，for 循环每转一圈，从服务器拿到一小块。

```python
for chunk in response:
```
每转一圈 = 服务器又送来一个 chunk（一小片答案）。这个循环本身就是"流式"的来源：来一片处理一片。

```python
    delta = chunk.choices[0].delta.content if chunk.choices else None
```
从这一小片里取出文字。流式模式下文字在 `delta.content` 里（不是非流式的 `message.content`）。`if chunk.choices` 是防线：有些 chunk 不带内容（比如收尾的统计帧），直接取 `[0]` 会 IndexError。

```python
    if delta:
```
有些 chunk 的 content 是 None（比如只声明角色那一帧），跳过，避免把 "None" 拼进文本。

```python
    full_reply += delta
    placeholder.markdown(full_reply + "▌")
```
拼接力：每个 chunk 只是一小片，必须累加。然后**重写同一个坑**为"目前累计的全部文本 + 光标"——覆盖式刷新就是打字机效果的本质。

```python
placeholder.markdown(full_reply)
```
循环结束后，最后一次覆盖刷新，去掉光标符，页面留下干净完整版。

```python
return full_reply
```
把完整文本交回给调用方——第 241 行用它写入 messages，记忆里存的永远是完整版。

**具体演变例子（假设模型要回答"你好呀"，分三片到达）：**

```
chunk1 delta="你好"  → full_reply="你好"   → 页面刷新为：你好▌
chunk2 delta="呀"    → full_reply="你好呀" → 页面刷新为：你好呀▌
chunk3 delta=None    → 跳过
循环结束             → 页面刷新为：你好呀（去光标）→ return "你好呀"
```

**完整数据流串起来：**

```
L234-235 挖坑（空）
L238 把坑的遥控器传给 ask_ai → ask_ollama
L61-66 每收一片就按一次遥控器刷新坑（打字机效果在这发生）
L67 返回完整文本
L241 完整文本写进 messages（供下轮重跑重画 + 发给模型的上下文）
```

## 记录 10：真流式 vs 假流式——关掉 stream 再本地拼接，效果一样吗

- **日期时间**：2026-09-04 18:38
- **关联主题**：AI应用/实战/AI智能伴侣、流式 vs 非流式的本质区别、首 token 延迟
- **状态**：已回答

### 问题原文

> 那现在这样跟原来的获取方式的区别是什么呢？现在不也是拿到full_reply后通过流式输出的方式拼接的结果么？如果我把 L52-69 这段代码 stream 关上，拿到一个完整的reply然后下面不变，采用流式拼接在页面上展示是不是也会得到同样的结果呢？

### 回答正文

你的判断对了一半：**视觉效果上，两种方式可以做到一模一样**——都是拿到文本后反复刷新 placeholder，页面上都是打字机。最终 full_reply 也一样。区别不在"页面怎么动"，而在**文字什么时候真正到达**。

**本质区别：循环的节奏由谁驱动**

- stream=True（真流式）：for 循环每转一圈的时机由**服务器推送**驱动——模型生成一个词就推过来一个 chunk。页面从第一个词到达就开始显示，用户等待时间 ≈ 模型生成第一个词的时间。
- stream=False（假流式）：必须等模型把**整段话全部生成完**，`response.choices[0].message.content` 才有值。这段时间页面上的坑是空的，用户在干等。然后才在本地对着一整段已有文本逐字刷新——那是在"演"打字机，节奏是程序自己控制的，和模型生成速度无关。

打个具体比方：真流式像看直播（主播一边写你一边看）；假流式像先下载完整视频再播放（等下载完才开始，只是播放有进度感）。总耗时相同，但假流式让你"先干等 N 秒，再看 N 秒动画"，真流式让你"看着它写完"。

**长回答时差距最明显**：回答要生成 20 秒，假流式就是空白 20 秒后才开始表演；真流式第 1 秒就有内容陆续出现。另外 stream=False 一次性等完整响应，中途任何网络抖动/超时就全盘失败；流式至少已显示的部分是拿到的。

**一个代码层面的细节**：把 stream 关上后"下面不变"是跑不起来的——L61-66 的 chunk 循环只在 stream=True 下成立；stream=False 时 response 是完整对象，直接 `response.choices[0].message.content` 拿全文，然后自己写一个"逐字/逐段刷新 placeholder"的动画循环。两种循环长得很像，但驱动力完全不同：一个被网络到达节奏推着走，一个是本地数据随便演。

## 记录 11：placeholder.markdown() 是什么？为什么用 markdown 不用别的

- **日期时间**：2026-09-04 18:41
- **关联主题**：AI应用/实战/AI智能伴侣、Streamlit 元素方法（markdown/text/write/code）、Markdown 格式
- **状态**：已回答

### 问题原文

> `ai_assitant.py#L65-66` 这里的markdown是什么语法？为什么这里用markdown不用别的？

### 回答正文

先澄清：`markdown` 不是 Python 语法，而是 **Streamlit 给占位符（坑）提供的一个"显示方法"**。`placeholder.markdown(x)` 的意思是：把字符串 x 显示在这个坑里，并按 **Markdown 格式**渲染。

Markdown 本身是一种轻量文本排版格式：`# 标题`、`**加粗**`、`- 列表`、`` `代码` ``。大模型的回答几乎都是 Markdown 写的，所以按 Markdown 渲染，回答里的加粗、列表、代码块才能显示出该有的样子。

**坑上的几种"显示方法"对比：**

| 方法 | 行为 |
|---|---|
| `placeholder.markdown(x)` | 明确按 Markdown 渲染 |
| `placeholder.text(x)` | 纯文本原样显示，`#`、`**` 都是字面字符 |
| `placeholder.code(x)` | 按代码块显示（等宽字体+语法高亮） |
| `placeholder.write(x)` | 万能但带猜测：根据类型自动选显示方式（字符串默认也走 Markdown） |

**为什么选 markdown：**

1. 明确、可预测——write 是"自动猜"，markdown 是"我说了算"，行为不会因传入内容变化而变。
2. 大模型回复天然是 Markdown，用它渲染观感正确；用 text() 显示的话 `**加粗**` 会原样露出星号。

**关键认知**：流式效果**不依赖 markdown 这个方法**。同一个坑上换 `.text()` 照样有打字机效果——流式的本质是"反复覆盖同一个坑"，用哪个显示方法只决定内容长什么样，不决定覆盖行为。换成 `placeholder.write(...)` 也能跑，效果基本相同。
